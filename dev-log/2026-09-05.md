## 更正推送结论：裸 push 会挂起，必须用完整模板（白皮书 v1.1.594）

- **更正对象**：v1.1.585 记录的"裸 `git push origin master` 直接可用"在本次复测中不成立，按项目"当前可复现事实优先"规则更正。
- **复测现象**：裸 `git push origin master` 挂起直到超时（退出码 124 / SIGTERM，且无输出）；清空代理后再试仍挂起；`git push --dry-run` 同样挂起；而只读的 `git ls-remote origin master` 秒回。本次提交仅 25 个对象、最大文件 17KB，排除数据体积因素，卡点在 send-pack 协商阶段。
- **根因两层**：① 系统级 `credential.helper=helper-selector` 在无 TTY 环境**挂起而非报错**（09-04 实验恰好未触发该路径）；② 期间 `~/.gitconfig` 的 `credential.helper` 被外部改写为 shell 形式 `!"C:/Users/YaoYinyu/.workbuddy/binaries/PortableGit/versions/1.2.0/mingw64/bin/git-credential-manager.exe"`，`!` 前缀表示经 shell 执行，无 TTY 时同样挂起。
- **凭据有效性旁证**：分别单独调用系统 GCM（`git credential-manager get`）与 PortableGit 目录下的 GCM，均能在 45 秒内返回 username/password（各 100 字节），证明**凭据一直有效，问题只在 helper 调用链路**。
- **处置**：把全局 `credential.helper` 改回直接调用形式 `manager`（改前备份为 `gitconfig.backup-20260905`）；实际推送采用完整模板——`GIT_CONFIG_SYSTEM` 指向 `C:/...` 原生路径空文件（绕过系统级 selector）+ 清空代理变量 + `GIT_TERMINAL_PROMPT=0` + `-c credential.helper=manager -c http.schannelCheckRevoke=false`，结果 `e8fd1ec..3e4f64e master -> master` 成功，`git ls-remote` 复验远端 HEAD 为 `3e4f64e`。
- **另一环境事实**：本机代理端口持续变化（09-02 为 2197、09-04 为 1786/7098、本次为 3697），curl 经代理访问 github.com 超时属正常，git 连通性一律以 `git ls-remote` 判定，不要以 curl 结果下结论。
- 结论：推送不需要用户提供任何凭证，但必须使用完整模板，不可依赖裸 `git push`。白皮书更新至 v1.1.594（新增更正条目并同步顶部版本号），MEMORY.md 推送章节同步修正。
