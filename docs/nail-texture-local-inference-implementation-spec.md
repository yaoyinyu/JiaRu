# 手部美甲纹理抠图模型端侧实施技术规范

版本：v1.13
日期：2026-10-30
状态：当前研发与端侧验收合同；Stage A+原尺寸Stage B研发中，PRODUCT HOLD，生产not-deployed
适用项目：JiaRu 美甲参考图纹理提取与 AR 试戴

## 1. 文档目的

本文档用于把“用户设备本地完成美甲纹理识别和抠图”的产品想法，落实为可实施、可测试、可验收、可回滚的工程方案。

本文档重点回答以下问题：

1. 端侧方案是否适合普通电脑和主流手机。
2. MVP 应承诺什么，不应承诺什么。
3. 模型训练、浏览器推理、后处理和纹理提取如何衔接。
4. 第一版、Beta 和正式发布分别使用什么验收标准。
5. 用户需要提供什么，工程侧需要完成什么。
6. 什么情况下可以继续、暂缓或回滚模型发布。

## 2. 结论与核心决策

### 2.1 总体结论

当前实施路线是离线训练、浏览器本地推理的两阶段甲面分割：Stage A产生候选和粗mask，Stage B用候选对应原尺寸RGB与粗mask输出完整mask及presence，再映回原图提取透明纹理并供/ar-tryon使用。完整输入/输出见§6.1/§6.3，当前模型与失败证据以白皮书§8.9/§11.1为准，下一活动只由Goal决定。

该路线仍在研发，未正式上线。模型质量和完整图WebGPU数值均有阻断；旧smoke加载通过不代表当前学得候选可用。产品manifest保持not-deployed，识别失败必须明确进入辅助定位与人工确认。

### 2.2 MVP 边界

MVP 包含：

- 用户上传一张本地参考图。
- 自动识别 1 到 10 个甲面实例。
- 输出每个实例的位置、置信度、方向和二值/软 mask。
- 从原始分辨率图片提取透明背景纹理。
- 允许用户移动、旋转、缩放、删除、补加和分配手指。
- WebGPU 不可用时回退到 WASM。
- 模型加载或推理失败时进入明示的辅助定位与人工确认；该路径不得计作正式识别成功。
- 图片不因识别和抠图流程被上传到服务器。

MVP 不包含：

- 在用户设备上训练或微调模型。
- 对摄像头每一帧运行完整 640×640 实例分割。
- 对任意图片承诺像素级完美边缘。
- 自动消除全部高光、阴影、透视和甲面曲率。
- 生成新的美甲设计。
- 医疗级或工业检测级指甲分割。

### 2.3 实时 AR 的边界

静态参考图纹理抠图与实时 AR 甲面跟踪是两条不同链路：

- 参考图：允许一次较重但高质量的实例分割。
- 实时 AR：使用手部关键点、低频检测和帧间跟踪，不应每帧运行全图实例分割。

如果未来需要实时分割，应采用“低频重新检测 + 高频关键点/光流跟踪 + 状态平滑”，而不是简单提高完整分割模型调用频率。

### 3.3 当前数据的正确定位

当前Stage B开发训练使用23个完整train源、149个完整甲面正例和5个同候选条件拒识，共154身份/462固定粗mask视图；完整真值、来源组、图片SHA和父血缘沿权威物化及重放继承。内部val、已消费保留8与正式保护数据不得回流train；当前训练域结果不能充当来源独立泛化证据。实际待审、隔离及角色入口见白皮书§8.8/§8.9与Goal，不按历史报告文件数或近重复ROI数累计来源。

任何新素材仍须完整源图质量、全部可见甲面、完整精确mask、合法性、零交叠与角色审核通过。AI或大模型候选没有自动真值资格；已参与错误分析/选择的材料不能再称下一候选未见发布留出。

## 5. 端侧部署策略

### 5.1 浏览器本地推理

浏览器本地推理是当前项目的主路线，原因是它与现有 Next.js、Canvas、ImageBitmap 和 Worker 架构一致，无需先引入桌面或移动原生容器。

执行后端优先级：

1. ONNX Runtime Web + WebGPU。
2. ONNX Runtime Web + WASM。
3. 明示的辅助定位/人工确认，不计正式模型成功。
4. 用户手动添加和修正区域。

### 5.2 设备分级

| 设备档位 | 推荐后端 | 推荐输入 | 产品策略 |
| --- | --- | ---: | --- |
| 桌面 Chromium，WebGPU 可用 | WebGPU | 512 | 当前正式质量口径；复用 Session |
| 中端 Android Chromium | WebGPU | 512 | 使用同一发布身份完成真机性能与内存门 |
| 桌面无 WebGPU | WASM | 512 | 接受更长等待，保持 UI 可取消并验证与WebGPU一致 |
| iPhone / Safari | WASM | 512 | 单独建立真机基线，不承诺与 Android 同速 |
| 极弱设备或运行时失败 | 辅助定位/人工确认 | 非模型输入 | 持续提示模型不可用，不计正式识别成功 |

当前发布合同固定512输入，不能按浏览器临时切换尺寸。384/448/640只能作为未来独立运行时变体；若启用，必须建立新的`releaseIdentity`并重新完成校准、正负发布留出、多后端一致性和对应真机门。

### 5.3 “本地处理”与“完全离线”的区别

本地处理表示图片不上传，推理发生在用户设备。

完全离线还要求：

- ONNX 模型已缓存或随应用分发。
- WASM 文件本地托管并可离线访问。
- MediaPipe 等第三方资产不依赖 CDN。
- 应用本身具备 PWA/Service Worker 缓存或桌面封装。

第一阶段承诺“图片本地处理”，不默认承诺首次访问即可完全离线。

## 6. 模型方案

### 6.1 正式候选模型合同

当前没有批准的正式候选，研发合同为：

- Stage A：单类别nail_texture的YOLO实例候选，当前开发训练/评估输入512方形letterbox；输出候选身份、粗mask和可映回原图的ROI。实际候选数上限、去重及分配必须随模型冻结。
- Stage B：原尺寸条件精修，batch1、float32四通道[1,4,H,W]（RGB归一化+同候选二值粗mask）；当前源码尺寸守卫16..1536，RGB不缩放。输出同尺寸mask logits和独立presence，两者均须验收；守卫支持不等于全尺寸浏览器资格通过。
- Stage B具体结构与训练见§6.3；该结构可独立完成精修，不要求Qwen在线参与。
- Stage A+Stage B全部权重、输入、ROI/候选分配、阈值、解码与运行时必须共同绑定同一releaseIdentity；正式阈值仅由新来源隔离val≥30校准，不能用旧test或训练域压力扫描选择。
- ONNX下载体积、初始化、端到端P95、完整峰值内存及稳定性按整条链实测。旧单模型15MB/8–12MB仅是性能目标，不能替代多模型总体成本与正式质量门。
- 先通过FP32完整图两头数值与实际mask质量，再考虑量化；不以量化或改阈值绕过失败。

生产manifest当前inputSize640只是not-deployed占位配置；不能当作当前512 Stage A或原尺寸Stage B已经部署。

### 6.2 输出协议与发布身份必须显式版本化

以下JSON保留单阶段/Stage A兼容示例，不能直接描述当前原尺寸双头Stage B或被当作已批准生产配置。正式接入前必须补齐并验收多资产、动态尺寸、ROI、双头及解码合同，且不得把旧384条件精修或六通道边界实验冒充当前四通道模型。

manifest 除现有字段外，建议逐步增加：

```json
{
  "schemaVersion": "nail-texture-manifest-v2",
  "version": "nail-texture-seg-v1",
  "candidateId": "candidate-N",
  "releaseIdentityCoreSha256": "",
  "runtimeSelectionLockSha256": "",
  "task": "segment",
  "inputSize": 512,
  "inputLayout": "NCHW",
  "colorOrder": "RGB",
  "normalization": "zero_to_one",
  "resizeMode": "letterbox",
  "preprocessContract": "square-letterbox-rgb-zero-to-one-v1",
  "backendPreferences": ["webgpu", "wasm"],
  "modelFile": "nail-texture-seg-v1.onnx",
  "outputContract": "ultralytics-seg-raw-v1",
  "postprocessContract": "nail-product-dedupe-v1",
  "scoreThreshold": 0.35,
  "labels": ["nail_texture"],
  "modelSizeBytes": 0,
  "sha256": ""
}
```

`outputContract`用于避免模型升级后输出维度变化却继续被旧后处理误读；`releaseIdentityCoreSha256`绑定candidate、全部模型、输入、阈值、预后处理和运行时锁等不含manifest自身哈希的规范核心，不能仅复制candidate名称。运行时选择锁也必须是pre-manifest锁，不得反向包含候选或生产manifest哈希。manifest写入该core哈希后再计算自身SHA-256，正式报告以“identity core + core哈希 + manifest哈希”形成最终`releaseIdentity`，从而避免manifest、选择锁与发布身份互相包含哈希的循环。上述v2字段是下一生产manifest的目标合同，当前加载器尚未全部实现，不能把文档示例误报为运行时PASS。

`scoreThreshold`是模型版本自身在全新来源隔离校准集上只选择一次的候选置信度阈值，必须是`0 < value < 1`的有限数。旧manifest缺省时继续使用`0.35`仅是兼容行为，不是新候选的校准证据；不得因诊断扫描直接修改共享默认值，候选还必须通过逐实例正样本、误检、候选数量、直接可用率和Beta门禁。

阈值校准必须只读取来源隔离的 `val` split，并绑定数据集、来源报告、模型权重、评估指标和预测制品哈希；`test`、冻结发布测试及其派生物一律不得用于选阈值。正式校准证据至少需要30张验证图、零无效真值polygon，并且全部验证图通过原分辨率完整甲面审核；校准器必须读取审核报告，校验dataset路径/哈希、逐标签SHA-256、审核覆盖数以及pass/rework/exclude计数，未提供或被拒绝的审核只能生成诊断结果。任一图片仍需返修/排除或存在漏甲、误标、重复、污染、裁断和未声明交叠时，整套split不得用于模型选择或阈值校准。真值合格后还须满足召回、每图误检和单图候选数门槛；条件不足时只能输出诊断点，`manifestScoreThreshold`必须为空。

### 6.3 两阶段原尺寸精修路线（当前研发）

当前按下列实际训练结构实施，技术权威接口见白皮书§8.9：

```mermaid
flowchart LR
  A[完整参考图] --> B[Stage A YOLO候选与粗mask]
  B --> C[稳定候选身份与原图ROI]
  A --> D[对应原尺寸RGB]
  C --> E[Stage B 四通道条件精修]
  D --> E
  E --> F[完整mask logits与presence]
  F --> G{有效甲面}
  G -->|接受| H[按原图坐标提取透明纹理]
  G -->|拒绝或执行错误| I[拒识或人工确认]
  H --> J[/ar-tryon]
```

1. Stage A负责候选召回。Stage B不能凭空恢复ROI之外或没有候选的甲面；必须分别报告候选覆盖与完整mask质量，不以候选数相等或ROI包含冒充贴边。
2. `model/training/native-pretrained-context-refiner.py`使用原生上下文编码/解码和粗mask先验，并复用已训练Stage A骨干第4/6/10层的stride8/16/32特征；骨干冻结且eval，三个可训练1×1投影向mask路径加入语义残差，presence从原e3特征读取。共有60个可训练张量414802参数、240个冻结骨干状态。
3. 现保留模型使用原RGB pack；通道光度规范化实验已完成独立60轮及全部重放，但因原147退化2项、压力220/298未过239门而关闭，未采用。该关闭实验在原pack前增加每ROI通道光度规范化：整数和/平方和、float64均值/标准差下限1，映射0.5均值/0.2标准差、裁至0..1并偶数舍入uint8，再执行原pack；Python/JS实现见白皮书§8.9。仅改变模型输入颜色，源图纹理不改，该配方已验收失败、未接生产，不将其输入合同施加给现保留模型。RGB保持原像素坐标；语义支路从归一化输入恢复对应uint8格点后/255（新候选对应规范化格点，非源图原色），只向右下pad32，按原图中心显式采样，不把pad压进ROI。mask和presence按固定合同解码；有效空输出只拒绝同候选，执行错误另记，不能用粗mask回填后算自动成功。
4. 完整精确真值监督、原图4像素距离辅助项和原图保持/增强配对策略见当前哈希绑定训练计划及白皮书。旧教师mask失败不得当新真值；目前Qwen3-VL-8B-Instruct/Qwen3.5-27B尚未参与训练或产品推理。
5. 后续才是学得权重导出、完整图ONNX/CPU/WASM/WebGPU一致性、多模型Worker与/ar-tryon接入及同身份正式验收。此图表示实施路线，不代表已上线。

这不是“只重打分而不替换mask”的旧stage2，也不是用颜色或磁吸边缘代替分割。旧candidate53/55/57、GrabCut和置信度图割分支的失败/关闭保留，不因本路线改写。

### 6.4 教师辅助与蒸馏的可选实验策略

当前已实施WeVisOne-VL-4B int4离线像素候选辅助标注：对完整原图调用本机像素解码器，保存原响应、框和全部实例float32 alpha；内部maxPixels262144只是候选计算配置，不证明原像素边界质量。不经过产品长边1600 JPEG/最多10实例截断路径；逐张完整原分辨率原图及轮廓实审，返修漏甲、阴影、皮肤和透明甲尖，只有通过的完整polygon作硬监督，未启用软目标蒸馏。首批3图17甲已并入26图166甲的Stage A 8轮训练，固定配对存在旧域退化，仍为开发候选；Stage B及生产权重不替换。真值/角色/执行证据入口见白皮书§8.8—§8.9。

Qwen3-VL-8B-Instruct和Qwen3.5-27B目前仅为离线视觉语义教师候选，未验证本项目效果。图文转文本或定位能力不等于像素mask教师；须先在已审train证据证明具体增益并冻结输出用途，不替代原分辨率真值审核、正式来源隔离和发布门。当前原图保持使用的是已有小模型RAW，不是Qwen蒸馏。

## 7. 预处理协议

训练、Python 评估和浏览器推理必须按阶段使用同一冻结协议。本节letterbox及RGB三通道0..1描述Stage A；Stage B是同候选原尺寸四通道、RGB按ImageNet均值/标准差归一化且粗mask为0/1，具体以§6.1/§6.3及实际pack源码为准，不得对Stage B套用512缩放。原图纹理采样和精修输入必须保留未被检测限幅缩小的原像素。

### 7.1 图片解码

- 处理 EXIF 方向。
- 将 alpha 与明确的背景策略统一处理。
- 过滤异常尺寸和损坏图片。
- 保留原始宽高，用于最终纹理采样。
- 检测输入最长边继续限制为 800 像素，避免高分辨率 RGBA 缓冲占用过大。

### 7.2 Letterbox

不得把任意横竖图直接拉伸为正方形。

预处理必须返回：

- `originalWidth`、`originalHeight`
- `resizedWidth`、`resizedHeight`
- `scale`
- `padLeft`、`padTop`
- `inputWidth`、`inputHeight`

模型坐标还原顺序：

1. 从模型坐标中去除 padding。
2. 除以 letterbox scale。
3. clamp 到检测输入范围。
4. 再映射到原始图片范围。

### 7.3 Tensor 格式

- 颜色顺序：RGB。
- 数据类型：FP32 基线。
- 数值范围：0 到 1。
- 内存布局：NCHW。
- batch：1。

预处理协议必须通过固定像素 fixture 测试，不仅测试 tensor 长度，还要测试颜色通道、采样位置和坐标逆变换。

## 8. Worker 与运行时设计

以下为既有Worker/ORT运行框架。当前原尺寸Stage B学得权重的完整部署合同及生产接入尚未通过，不能把旧stage2评分器、384条件精修或smoke加载视为当前模型已上线；正式组合仍须按§6.1/§6.3及白皮书§8.9验收。

### 8.1 环境识别

不能使用“是否存在 `window`”区分浏览器和服务端，因为 Web Worker 本来就没有 `window`。

建议区分：

- 主线程浏览器：存在 `window` 和 `document`。
- Worker 浏览器：存在 `self`、`WorkerGlobalScope` 或 `OffscreenCanvas`，且不存在 `document`。
- Node.js/服务端：不存在浏览器 Worker 所需能力。

### 8.2 ONNX Runtime 加载

目标：让 Next.js 构建器明确收集 ONNX Runtime 和所需 WASM 资产。

要求：

- 避免用 `new Function()` 隐藏包导入。
- WebGPU 与 WASM 使用可被构建器分析的明确入口。
- 确保 WASM 文件的 URL 与部署路径一致。
- WebGPU Session 创建失败后，允许重新创建 WASM Session。
- Session 按“模型版本 + 后端 + 输入尺寸”缓存。
- 切换模型版本或后端时显式释放旧 Session 和 GPU 资源。

### 8.3 Worker 生命周期

- 通过 Transferable 传输 `ImageBitmap`。
- Worker 内复用 Session，不为每张图重新初始化模型。
- 支持取消、超时和组件卸载清理。
- 同一时间限制并发识别数量，避免多张图造成内存峰值叠加。
- Worker 崩溃后能够重建，并把当前请求安全回退到规则识别。

### 8.4 运行时状态

UI 至少显示或记录：

- `backend`: model / fallback
- `executionProvider`: webgpu / wasm
- `modelVersion`
- `coldStartMs`
- `elapsedMs`
- `workerElapsedMs`
- `warnings`

产品界面不必暴露全部调试字段，但调试导出必须保留。

## 9. 模型后处理协议

### 9.1 真实输出契约验证

接入首个真实模型时必须保存：

- 输入名称与维度。
- 每个输出名称与维度。
- 小规模输出 sample。
- 模型版本和导出配置。
- 与 Python 参考推理的结果对照。

不能依靠测试 fixture 猜测真实 YOLO 输出布局。

### 9.2 建议处理顺序

1. 识别输出 tensor 和维度布局。
2. 必要时把通道优先输出转置为候选行。
3. 计算类别置信度。
4. 过滤低置信度候选。
5. 限制预 NMS Top-K。
6. 执行 NMS。
7. 限制最终 1 到 10 个候选。
8. 只为最终候选解码 mask。
9. mask 按候选框裁切。
10. 去除 letterbox padding 并映射回原图。
11. 计算主方向、质量提示和建议手指。

### 9.3 性能约束

- prototype tensor 只转换或读取一次。
- 不为每个候选重复 `Array.from` 整个 prototype。
- 不为被置信度或 NMS 淘汰的候选解码 mask。
- 尽量复用 typed array 和临时缓冲。
- 保留候选数量上限，避免异常图片产生不可控计算量。

### 9.4 mask 质量处理

- mask threshold 必须由真实验证集调参。
- 仅进行轻量孔洞填充、孤立点去除和边缘羽化。
- 形态学操作不能明显吞掉细窄法式边或尖甲轮廓。
- 模型 mask、后处理 mask 和用户修正结果必须能分别记录，以便定位误差来源。

## 10. 透明纹理提取

### 10.1 原图采样

模型只负责在缩小图上定位和分割，最终纹理必须从原始分辨率图片采样，以避免模型输入尺寸限制纹理细节。

提取流程：

1. 将 mask 映射回原图。
2. 计算甲面紧致边界。
3. 按方向旋转到统一朝向。
4. 生成带 alpha 的纹理图。
5. 对边缘进行小半径羽化。
6. 输出 `ImageBitmap` 或等价浏览器纹理资产。

### 10.2 高光处理

高光修复属于纹理恢复，不属于基础分割，必须独立控制。

要求：

- MVP 默认保留原始高光。
- 高光修复作为可关闭的增强选项。
- 白色法式边、珍珠、银白、镜面和低饱和设计必须加入专项测试。
- 高光修复前后分别保留诊断结果，不能不可逆覆盖唯一纹理资产。

### 10.3 透视与曲率展开

首版可以只做旋转和紧致裁剪。

当真实测试表明甲面透视导致 AR 纹理明显变形时，再引入四点透视或 TPS 展平。该能力应通过产品可用率证明必要性，而不是提前增加模型复杂度。

## 11. 数据方案

### 11.1 数据角色

| 数据类型 | 允许角色 | 发布证据约束 |
| --- | --- | --- |
| AI合成正样本 | train、训练增强、消融 | 不得替代真实域正样本发布留出；生成批次必须按同一`sourceGroup`隔离 |
| standing授权真实参考图 | train、开发折、全新校准或全新发布留出中的唯一一种 | 同一图片、父图、近重复和稳定`sourceGroup`只能分配一个角色 |
| 真实产品用户图 | 失败案例、Beta或在产品侧另有明确数据使用依据后的训练/评测 | 项目开发standing授权不自动覆盖未来终端用户上传数据；必须遵守产品采集时的实际许可与退出选择 |
| AI困难负样本 | train或独立压力留出中的唯一一种 | 可用于零误检压力门，但不能替代真实域负证据；被模型筛选后不得再充当下一候选未见留出 |
| 真实负样本 | train、失败案例或全新独立留出中的唯一一种 | 必须按来源组隔离并记录是否曾被候选推理/选样 |
| 旧val30、旧test100、已消费holdout | 只读受保护历史回归 | 永久禁止训练、配方/阈值/数据选择及再次冒充最终未见证据 |

### 11.2 真实数据覆盖

真实数据至少覆盖：

- 不同肤色、手型和年龄段外观。
- 裸甲、透明甲、浅色甲、深色甲和黑色甲。
- 法式边、猫眼、亮片、珍珠、镜面、渐变和复杂图案。
- 圆甲、方甲、尖甲、长甲、短甲和人工甲片。
- 单甲、单手和双手；独立甲片板、练习甲或非手上模板只进入单独压力测试/失败案例，不冒充真实手上正域。
- 横图、竖图、方图和不同分辨率。
- 可确认全部应标甲面轮廓的远景、近景和低照度；任何应标甲面被裁边，或运动模糊/失焦到无法确认完整轮廓的正图必须在源图门排除，可另存为失败案例但不得进入正训练。
- 戒指、饰品、手指互相遮挡和复杂背景。
- 无美甲图片、花瓣、珠宝、印刷纹理等 hard negative。

### 11.3 数据规模是阶段性目标

数量不是质量保证，以下范围仅用于安排工作量：

| 阶段 | train / 开发证据 | 校准 | 一次性正样本发布留出 | 困难负样本发布留出 | 目的 |
| --- | --- | ---: | ---: | ---: | --- |
| 工程冒烟 | fixture或少量样例 | 0 | 0 | 0 | 验证链路，不判断泛化 |
| 模型试验 | 足够覆盖目标长尾的来源组，使用train内部开发折 | 0 | 0 | 0 | 低成本判断配方能否学习真实域 |
| 候选冻结 | 原分辨率真值与角色隔离全部通过 | ≥30张全新来源，只选一次阈值 | ≥100张，运行时锁定后原子冻结且只评估一次 | 候选锁定后另建≥100张全新未见样本 | 建立不可变发布资格 |
| Beta / 正式发布 | 不再修改权重和运行时 | 使用已锁定阈值 | 保持只读 | 保持只读并通过三变体零误检/零delta | 用同一`releaseIdentity`验证产品体验、设备和回滚 |

如果样本高度重复，即使数量达标也不能通过 readiness gate。

### 11.4 数据拆分

必须按以下信息分组拆分：

- 用户或来源。
- 拍摄 session。
- 连拍批次。
- 同一商家或同一套图。
- AI 生成批次。

同一组不得跨 train、val、test。近似重复图必须在拆分前检测和归组。

### 11.5 标注与授权

- 每张图片保留来源、许可声明、授权范围、创建时间、稳定图片身份、`sourceGroup`、用途角色和SHA-256。
- 用户已对本项目范围内由其提供或放置、且有权授权并可由Codex访问的图像资源与本机计算资源授予standing商业模型开发使用权；逐批、逐清单、训练启动和满足机器证据门后的原子freeze无需再次请求确认。
- 精确清单、来源、用途、角色和SHA-256仍须由机器绑定并重放，用于追溯与隔离，不是人工批准等待点。该授权不允许已消费test/holdout回流训练，也不替代未来产品终端用户上传数据的实际许可、外部付费服务或真实Beta/物理设备证据。
- mask 必须贴合真实甲面，不使用固定模板替代人工复核。
- 记录遮挡、人工甲片、甲面形状、质量等级和失败原因。
- 标注审计 error 必须为零；warning 必须人工确认后才能用于正式训练。

## 12. 评测指标与明确口径

### 12.1 模型指标

- box mAP50。
- mask mAP50。
- AP75 和 mAP50:95。
- Dice / IoU。
- Boundary-F1。
- 每图漏检率。
- 每图误检数和 hard negative 误检率。
- 方向角误差。

### 12.2 产品指标

#### 直接可用率

定义：候选纹理无需移动 mask、补边或删除背景，即可被审核者接受用于 AR 试戴的实例比例。

必须明确：

- 纯粹调整手指分配是否仍算直接可用。
- 轻微旋转是否算直接可用。
- 由几名审核者判断以及分歧如何处理。

建议正式口径：不修改甲面几何和 alpha 边缘即可使用；仅改变手指分配不视为抠图失败。

#### 背景/皮肤泄漏率

建议按实例计算：

```text
leakageRate = predictedMask 中位于 GT 甲面外的面积 / predictedMask 总面积
```

#### 甲面缺失率

```text
missingRate = GT 甲面中未被 predictedMask 覆盖的面积 / GT 甲面总面积
```

泄漏率和缺失率必须分别报告，避免通过缩小 mask 人为降低污染率。

#### 人工修正成本

- 需要修正的实例比例。
- 每张图平均修正时间。
- 删除、补加、移动、旋转和修边的操作次数。

### 12.3 分组指标

总体平均值不能掩盖特定人群或场景失败。至少按以下维度报告：

- 肤色区间。
- 甲色深浅。
- 反光/非反光。
- 遮挡/无遮挡。
- 横图/竖图。
- 单甲/多甲/甲片板。
- 简单背景/复杂背景。
- 目标设备和执行后端。

## 13. 性能测量口径

### 13.1 冷启动

冷启动单独统计：

- 模型下载或缓存读取。
- WASM 资产加载。
- WebGPU adapter/device 初始化。
- ONNX Session 创建与图优化。

冷启动可以超过热推理预算，但必须显示明确加载状态，并避免重复发生。

### 13.2 热推理端到端时间

热推理从用户图片已经解码后开始，覆盖：

1. 检测图缩放和像素准备。
2. `createImageBitmap`。
3. Worker 排队与传输。
4. tensor 预处理。
5. ONNX 推理。
6. NMS 和 mask 后处理。
7. 候选返回主线程。

正式报告使用 P50、P95 和最大值，不只使用单次平均值。

### 13.3 建议性能门槛

| 配置 | 阶段 | 门槛 |
| --- | --- | ---: |
| 桌面 Chromium + WebGPU | Beta/正式，热推理端到端 P95 | <800ms |
| 中端 Android + WebGPU | Beta/正式，热推理端到端 P95 | <1500ms |
| 桌面 WASM | 首轮先建立基线 | 基线后冻结门槛 |
| iPhone / Safari WASM | 首轮先建立基线 | 不直接套用 Android 门槛 |

移动端正式门槛必须绑定具体设备档位、浏览器版本、输入尺寸和模型版本。

### 13.4 内存与稳定性

- ONNX 文件 <15MB，理想 8–12MB。
- 移动端识别链路增量峰值内存建议控制在 128–150MiB 以内。
- 连续运行至少 20 次后，内存不能持续单调增长。
- Worker 取消或崩溃后必须释放 `ImageBitmap` 和临时缓冲。
- 同一时刻默认只运行一个识别请求。

内存门槛需要通过真机基准确认，不能只根据 tensor 理论体积推断。

## 14. 分阶段验收标准

### 14.1 阶段 A：工程冒烟版

目标：证明浏览器确实在本地运行真实 ONNX，而不是继续使用 fallback。

必须通过：

- Worker 可识别浏览器 Worker 环境。
- ONNX Runtime 能被构建并加载。
- WebGPU 或 WASM Session 创建成功。
- UI 显示真实模型版本和执行后端。
- 模型失败后进入明确的“辅助定位/人工确认”流程；无像素mask的fallback不得显示为正式识别成功。
- 取消和超时正常。
- 横图、竖图和方图坐标逆变换正确。
- 至少一个真实 ONNX 输出 fixture 进入自动测试。

本阶段不设置 mAP 和直接可用率门槛。

### 14.2 阶段 B：模型试验版

目标：用train内部按`sourceGroup`互斥的开发折证明候选配方能学习完整甲面分割，并以较低成本淘汰失败方向。

建议门槛：

- mask mAP50 ≥0.65（诊断指标）。
- box mAP50 ≥0.75（诊断指标）。
- 直接可用率 ≥60%。
- 单模型ONNX目标<15MB；若超过，必须提前用真实浏览器体积、初始化、P95和峰值内存决定是否继续。
- train开发折没有来源或近似重复泄漏，且不得读取旧val30、旧test100或任一发布留出逐图证据。
- 能形成可解释的失败类型清单。

该门槛只用于train内部实验筛选，不生成正式候选PASS。每轮至多两个短程单变量实验；只有一个胜出配方可进入全量训练和全新校准集。

### 14.3 阶段 C：Beta

目标：在受控用户范围内验证真实产品体验。

建议门槛：

- mask mAP50 ≥0.75。
- box mAP50 ≥0.85。
- 直接可用率 ≥80%。
- 桌面 WebGPU 热推理 P95 <800ms。
- 中端 Android WebGPU 热推理 P95 <1500ms。
- fallback、手动修正和取消能力完整。
- 真实失败样本能够进入授权复核流程。
- Beta、浏览器和性能证据必须绑定同一`releaseIdentity`；fallback样本不计入模型直接可用率。

### 14.4 阶段 D：正式发布

必须通过：

- 配方锁定后使用不少于30张、与train及发布留出来源隔离的全新校准集，仅选择一次阈值；旧val30不得满足该门。
- 权重、512预处理、阈值、后处理和`releaseIdentity`锁定后，原子冻结不少于100张全新正样本发布留出并只正式评估一次。
- 正样本逐实例质量门固定为：实例召回率≥0.90、完整mask比例≥0.85、漏甲图片率≤0.10、加权杂散率≤0.02，并要求每图均有可核验输出；mAP只作辅助诊断。
- 候选锁定后另建不少于100张、未被当前或前代模型筛选的全新困难负样本，原图、裁右下12%、模糊右下角均达到误检图片数=0、误检检测数=0、相对原图delta=0；非右下水印还须增加对应区域消融。
- 直接可用率 ≥85%。
- 明显皮肤/背景污染实例比例 <10%，并同时报告像素级泄漏率。
- 粗糙矩形化实例比例 ≤15%。
- 主要场景分组没有不可接受的明显退化。
- Windows桌面性能/重复运行内存、真实用户失败案例、Android手机、Android平板、iPhone和iPad各至少20次真实验收通过。
- 训练框架、ONNX、WebGPU和WASM在同一冻结样本上的候选数量、置信度、坐标和像素mask一致。
- 模型manifest、大小、SHA-256、指标和发布记录完整，且所有报告绑定同一不可变`releaseIdentity`。
- 至少100张Beta人工质量审核和正式产品质量报告通过。
- 完成双版本回滚bootstrap：一个完整批准版本登记为非当前fallback，另一个不同权重且完整批准版本作为current，并实际验证一键回滚。

## 15. 测试策略

### 15.1 单元测试

- Letterbox 和坐标逆变换。
- RGB/NCHW tensor 生成。
- 输出布局识别和转置。
- 置信度过滤、Top-K 和 NMS。
- mask coefficients × prototype 解码。
- box crop、padding 去除和原图映射。
- 方向估计和候选排序。
- 泄漏率、缺失率和直接可用率统计。

### 15.2 真实输出 fixture 测试

每个支持的 `outputContract` 至少保存一个真实模型输出 dump，并验证：

- 输出名称和维度。
- 候选数量。
- 至少一个候选坐标。
- mask 前景像素范围。
- 与 Python 参考后处理的一致性。

### 15.3 浏览器集成测试

- WebGPU 成功路径。
- WebGPU 失败转 WASM。
- ONNX 加载失败转 fallback。
- Worker 不可用转主线程或 fallback。
- 超时、取消、组件卸载和重复上传。
- 图片全程无识别上传请求。

### 15.4 视觉回归

固定真实样本覆盖：

- 横图和竖图。
- 深色、浅色、透明和镜面甲。
- 法式边和细线图案。
- 复杂背景和遮挡。
- 单甲、五甲和甲片板。

### 15.5 性能测试

- 冷启动与热推理分开。
- WebGPU 与 WASM 分开。
- 输入尺寸分开。
- 桌面、Android 和 iPhone 分开。
- 至少多次运行后计算 P50/P95。
- 同时报告 Worker 时间、主线程开销和峰值内存。

## 17. 推荐执行顺序

### 里程碑 1：修复发布证据基础设施

本项audit v3、身份和消费台账基础已具备，当前不重复建设；实际活动转里程碑2并以Goal为准。以下保留该基础合同。

1. 实现audit v3的active gate语义，保留历史失败但不让其永久阻断未来候选。
2. 建立统一`releaseIdentity`与全新正样本发布留出的一次性消费台账。
3. 把固定逐实例正样本合同接入最终总门，并拒绝跨候选/跨运行时证据拼接。
4. 同步进度dashboard、实施规范和完成度说明；旧val30/test100明确只读历史回归。

完成定义：即使历史中存在真实失败，未来同一发布身份仍可以通过一条完整、可重放且不可拼接的当前证据链得到`complete`。

### 里程碑 2：两阶段候选研发与冻结

1. 当前唯一活动与完成事实只读Goal；候选召回、原尺寸完整mask及拒识分别验真，固定完整分母、可达性、单次预算及停止条件，避免重复已证伪配方。
2. 精确硬真值为主线，原图保持/增强或新教师实验必须有可验证依据、固定最后权重和完整实例迁移；不读取受保护旧val/test/holdout用于选择，不把训练域改善当泛化。
3. 补齐来源隔离新val≥30后一次校准，锁定两阶段所有资产、各自实际输入/坐标、阈值、预后处理与releaseIdentity。
4. 另冻新正样本发布留出≥100一次验收，达到0.90/0.85/0.10/0.02合同，不能用历史512单阶段或高尺寸诊断覆盖当前部署口径失败。

完成定义：同一不可变身份通过新来源正样本发布门；训练完成或开发门通过只是中间证据。

### 里程碑 3：负样本、生产资产与产品验收

1. 候选锁定后另建不少于100张未被模型筛选的全新困难负样本，完成三变体零误检/零delta及水印位置消融。
2. 导出生产ONNX并验证训练框架、ONNX、WebGPU、WASM候选/坐标/mask一致性，manifest绑定同一`releaseIdentity`。
3. 修复fallback语义并完成真实浏览器、Windows桌面性能/内存、真实用户失败案例和Android手机/平板、iPhone/iPad各至少20次验收。
4. 完成Beta不少于100张、正式产品质量、双版本回滚bootstrap和实际演练。

完成定义：同一`releaseIdentity`的全部当前正式门经audit v3重放为`ok=true`、`decision=complete`；此前任何单项PASS都只是中间里程碑。

| 合成数据与真实图片域差异 | 测试漂亮但真实失败 | 合成图不进入正式 test，优先补真实授权数据 |
| 同来源数据跨 split | 指标虚高 | 按用户、来源、session 和近似重复分组拆分 |
| 浏览器预处理与训练不一致 | 坐标和准确率异常 | 固定 letterbox、归一化和颜色协议，并做 fixture |
| 模型输出布局变化 | 候选被错误解析 | manifest 增加 `outputContract` 并保存真实 dump |
| mask 解码内存过高 | 手机卡顿或崩溃 | 先 Top-K/NMS，再解码最终 mask，复用缓冲 |
| WebGPU 不可用或算子不兼容 | 模型初始化失败 | WebGPU → WASM → 明示辅助定位/人工确认；不得把规则fallback计为模型成功 |
| 高光修复破坏白色纹样 | 纹理语义丢失 | 默认关闭，作为独立增强并专项评测 |
| 透明甲和肤色接近 | 边缘泄漏或缺失 | 增加真实困难样本、Boundary-F1 和泄漏/缺失指标 |
| 弱手机性能不足 | 等待过长 | 当前512发布身份在该设备验收失败时不宣称支持；384/448只能作为另行校准、留出评估和真机验收的独立发布变体 |
| 用户图片隐私 | 产品信任风险 | 默认不上传；项目开发standing授权不自动覆盖未来产品终端用户上传数据，训练回流须依据实际产品许可 |
| 模型升级回归 | 已有场景变差 | 固定真实回归集、版本登记和一键回滚 |

## 19. 发布决策

### Go

满足当前阶段全部硬门槛，且没有真实测试集泄漏、隐私问题或不可接受的设备崩溃。

### Hold

出现以下任一情况时暂停 promotion：

- 指标通过但真实直接可用率不足。
- 真实模型仅在 fallback 下显示成功。
- 性能样本不足或目标设备缺少报告。
- 模型输出协议与后处理实现未锁定。
- 数据来源、standing授权绑定、用途角色、清单或SHA-256机器证据不完整；不得把该机器缺口转写为重复向用户索要逐批授权。
- 当前候选证据没有绑定同一`releaseIdentity`，或使用旧val30/test100/已消费holdout冒充全新校准与发布留出。
- 某一重要场景分组明显退化。

### No-Go / 回滚

- 用户图片被非预期上传。
- 模型导致页面崩溃或持续内存增长。
- 发布模型无法在目标后端初始化，且 fallback 也失效。
- 新模型对固定真实回归集产生重大质量退化。
- 模型文件、manifest、SHA256 或发布记录不一致。

## 22. 最终落地判断

本方案不是依赖高端显卡才能成立的重型方案。对于“单张图片、单次识别、选择满足质量门的最小模型、输入限幅、Worker推理、WebGPU/WASM分级和人工可修正”的产品边界，它可以适配普通电脑和主流手机；实际可发布性必须由生产ONNX在目标浏览器与设备上的体积、初始化、P95和峰值内存证明。

正式落地的关键不是继续增加模型复杂度，而是依次完成：

1. audit v3的active gate、逐实例强门、统一`releaseIdentity`和发布留出消费台账。
2. train内来源组开发折、全新校准集与锁定后的一次性正样本发布留出。
3. 新来源训练数据、完整mask和全新困难负样本三变体零误检门。
4. 生产ONNX与训练框架/WebGPU/WASM输出一致，manifest和全部验收证据绑定同一身份。
5. fallback人工语义、真实浏览器/桌面/四类真机、Beta100、产品质量和双版本回滚。

只有当上述证据完整时，才能从“技术上可行”升级为“可正式发布”。
