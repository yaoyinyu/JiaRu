# 甲如项目全面分析与改进建议（2026-09-05）

编写：Codex。依据当前工作区源码、配置、已有机器报告、局部行为复现和本轮工程检查。此报告是项目评审，不是新的模型验收或法律合规结论。

## 总体判断

甲如已有可继续发展的产品原型：图片编辑、双引擎 AI 生图、图库、本地收录、AR 辅助定位和账号原型都存在；图库→编辑器灵感、图库/收录→AI/AR、AI→本地收录的链路已经打通。数据来源隔离、真值审核、哈希绑定和失败保持 HOLD 也已有较完整的工程基础。

当前主要矛盾是能力成熟度不均：核心精细识别仍未达到发布门；账号、成本保护和隐私告知落后于已经暴露的功能；大量审计与测试尚未完全覆盖真正的页面交互和生产生命周期。优先投入应转向核心任务成功率和发布可靠性，暂缓扩展更多引擎、商户交易和复杂 3D 能力。

## 优先级与证据

P1 表示对应能力公开上线前应解决，或下一次正式模型评估前应解决；P2 表示明确功能缺陷或应排期的可靠性改进。它们不是对所有模块统一禁止本地试用的结论。

### 1. P1：精细识别尚未形成稳定的整图可用能力

当前 candidate57 报告：

| 指标 | 当前结果 | 正式门/解释 |
| --- | --- | --- |
| 实例召回 | 531/554，95.85% | ≥90%，通过 |
| 完整 mask 比例 | 479/554，86.46% | ≥85%，通过 |
| 存在漏甲的图片比例 | 13% | ≤10%，失败 |
| 加权杂散率 | 4.693% | ≤2%，失败；不是简单的误检图片比例 |
| 可直接提取整图 | 59/100，59% | 报告定义的诊断指标，不等同真实用户满意率 |

证据：`model/training/candidate57-frozen-test100-decision-v1.json:39`。生产目录只有 manifest，没有其指向的 ONNX；当前页面依赖已有辅助定位与人工补选。实例指标较高并不代表每张图都能直接完成任务。

建议：继续保持 candidate57 HOLD；把整图直接可用率、每图修正次数、修正耗时、透明/低对比/长甲等来源分组结果作为产品观察项。下一候选由独立 train 证据或事先登记的训练改动驱动，不利用此次 test100 逐图结果反调。

### 2. P1：最终完成度审计没有接入最关键的逐实例质量门

`scripts/audit-nail-texture-local-inference-completion.ts:803` 的候选模型指标门仍以 box mAP50≥0.85、mask mAP50≥0.75 判断；`:1093` 起的正式 gates 没有单独的完整 mask、漏甲图片率与加权杂散门。默认 `model/reports/nail-texture-completion-evidence-profile.json:5` 仍绑定 candidate5 的历史证据，与当前 candidate57 脱节。

当前最终结果仍为 HOLD，并未观察到错误放行。问题是核心阻塞没有成为不可绕过的机器门，后续其他门补齐后仍可能得到不完整的“完成”证据。

建议：以运行时选择锁统一候选身份，把 schema v2 正样本报告及深度重放接入正式 gates，同时验证独立正样本留出的资格；历史 profile 明确只用于历史诊断。应补“mAP 通过但逐实例门失败时最终必须 HOLD”的集成用例。

### 3. P1：test100 的单次评估规则缺少可执行的消费登记

`model/training/evaluate-candidate57-frozen-test100.py:68` 检查不可变选择锁中的 `protectedTest100Used=false`，`:149`、`:157` 只要求输出目录全新；`:372` 起在新报告中固定记录 `evaluationCountForLockedCandidate=1`。执行器没有读取终结决策，也没有独立的已消费台账。当前选择锁仍为 false，终结决策已为 true。

因此，现有脚本不能阻止同一选择锁换输出目录再次评估。这是静态控制流确认；本轮没有重跑受保护测试，也没有证据表明有人实际违规重跑。

建议：按“选择锁 SHA-256 + 测试快照 SHA-256”建立追加式运行台账，在首次读图/推理前原子占用，并区分未读图失败、已推理失败、结果已生成三个阶段。保留原选择锁字节用于重放，不应通过修改历史锁来模拟消费记录。

### 4. P1：固定 val30 的反复选择使小幅改进缺少独立支撑

`candidate57-low-band-margin-gate-plan-v1.json:11` 列出的两个真阳性 margin 为 0.56767/0.58569、两个假阳性为 0.53927/0.52649，`:36` 的阈值 0.55 正好位于两组之间。它符合现行 val 校准规则，但局部提升依赖很少的边缘实例。`candidate52-generated-positive-boundary-training-plan-v1.json:22` 还记录了基于历史 val 表现改变训练损失，下一行跳过影子开发集。

这构成方法学风险，不能据此断言已经证实过拟合。自适应重复使用同一留出集可能拟合留出集本身，见 [Dwork 等，Generalization in Adaptive Data Analysis and Holdout Reuse](https://arxiv.org/abs/1506.02629)。

建议：在 train 内按 sourceGroup 隔离开发集用于配方选择，辅以来源组交叉验证或区间估计；新来源 val 用于最终校准。旧 test100 保持受保护回归身份，在模型、数据和后处理完全锁定后冻结全新正样本发布留出。不要靠放宽既有门槛制造成功。

### 5. P1：已实现账号，但付费 AI 接口尚未使用鉴权和费用保护

`src/app/api/generate-ai/route.ts:43`、`src/app/api/generate-seedream/route.ts:42` 在参数验证后直接调用供应商，未调用现有 `requireUser`，也没有按用户/全局配额、并发上限、预算熔断与幂等任务记录。

触发条件是接口公开可达且服务端配置了有效供应商密钥；此时任意调用者都可发起消耗额度的请求。本轮没有检查当前公网暴露，也没有调用付费服务。

建议：统一两路 API 的身份与额度校验、原子额度预留、任务 ID 和结果查询。游客体验可保留，但应有明确预算与服务端约束。补生成成功率、耗时分位数、失败类型、单次成本和总预算监测；客户端取消与后台任务状态应衔接，避免离开页面后无法找到已生成结果。

### 6. P1/P2：账号原型缺少生产登录与持续会话闭环

`src/lib/auth/sms.ts:43` 在生产模式未配置供应商时抛错，配置 `SMS_PROVIDER` 后仍抛“尚未接入”，所以现有手机短信登录尚不能作为生产能力。`src/app/api/auth/request-code/route.ts:29` 在开发模式返回 devCode；如果将开发服务器经隧道公开并连接真实账户库，会失去真实号码所有权验证，因此演示必须使用隔离测试库。

`src/lib/auth/cookies.ts:21` 的 access cookie 为 2 小时；`src/lib/auth/http.ts:11` 只使用 access。虽然 service 已有 `rotateTokens` 及单测，但当前 src 没有调用它的续期接口或前端流程，30 天 refresh cookie 无法维持实际登录。

建议：补真实短信适配与生产配置预检；接入有并发处理的刷新流程；明确开发认证仅适用于测试。运行环境说明也需统一：README 的 Node≥20 与使用 `node:sqlite` 的源码不匹配，package.json 尚无 engines 约束。持久数据库目录、备份恢复、验证码状态的多实例共享需要明确部署方案。

新部署还有已复现的初始化缺口：`auth/config.ts:7` 默认使用 `data/jiaru-user.db`，`server.ts:18` 直接调用 `db.ts:125` 的 `new DatabaseSync`，src 没有创建父目录的逻辑。使用唯一临时路径且父目录不存在时，实测得到 `ERR_SQLITE_ERROR: unable to open database file`（errcode=14），没有生成任何文件。按 `/api/me`→requireUser→getAuthService 的调用链，干净克隆首次匿名请求也会在认证判断前抛错；HTTP 500 为源码推导，未启动新服务验证。应增加目录初始化/可写性预检，明确生产持久卷。

### 7. P2：验证码防护和手机号身份一致性存在已复现缺陷

`src/lib/auth/captcha.ts:81` 把答案放进 SVG 的 `<text>`，再 base64 返回；解析文本即可得到验证码答案。`service.ts:153` 的发送间隔/每日限额从验证码表计算，成功登录在 `:201` 删除记录，`db.ts:177` 因而丢失已消费的发送历史。纯内存复现确认发送计数 1→0，成功登录后可立即再次发送。

另在 `service.ts:251`，已有手机身份 A 的用户再次 bindPhone(B) 会更新 users.phone，但已有 identity 不更新；纯内存复现确认资料为 B、登录身份仍为 A，随后 B 登录触发 `UNIQUE constraint failed: users.phone`。解绑也需同步检查资料与身份一致性。

建议：发送台账与验证码生命周期分离，限流检查/配额预留原子执行；图形挑战不能直接暴露机器可读答案。明确补绑与换绑规则，并在事务内更新用户资料、身份、唯一性和验证码消费。增加“成功使用后再次发送”“换绑后新旧号码登录”“解绑后再绑定”的行为用例。

### 8. P2：编辑器导出清晰度与重置行为不符合用户预期

`src/components/NailCanvas.tsx:68` 将画布限制为最多 400×600，`:185` 直接导出该预览画布。4096×4096 上传图最终只能保存为 400×400，像素数量仅保留约 0.95%。应将显示尺寸与输出尺寸分开，用原图和可重放的笔画/图层生成成品。

同组件 `:87` 的历史队列仅保留 20 份，`:181` 用 history[0] 重置；第 20 笔开始原图快照被淘汰。直接复用源码表达式的模拟确认，25 笔后重置回到第 6 笔。应独立保留原始状态，撤销历史不能替代原图基线。

### 9. P2：AI 比例选择和 AR 纹理释放存在局部缺陷

从 `src/app/ai-generate/page.tsx:60` 抽取当前函数执行，标准 3:4 被映射为 2:3，标准 2:3 被映射为 9:16。此结果会写入生成请求，增加构图变化风险；供应商实际改图程度本轮未测。建议按支持比例计算距离，并覆盖全部标准比例的自映射。

`src/app/ar-tryon/page.tsx:229` 在“应用全部”时逐项检查旧数组是否还有共享引用。A 纹理被四指共享、第五指为 B，再将 B 应用全部时，每个 A 都看到另一个 A，因此均跳过 close。直接执行该段逻辑确认 A 最终无槽位引用但 close 次数为 0。应比较更新前后的唯一 bitmap 集合，关闭所有不再保留的资源。已有其他资源释放措施，不应概括为整个 AR 完全未管理资源。

### 10. P1/P2：隐私告知与同意偏好没有统一事实口径

`src/app/privacy/page.tsx:7` 仍称“没有用户账户体系”，`:12` 仅列 Agnes，遗漏 Seedream；`:19` 声称关闭改进计划后不再上传任何数据，但主动 AI 生成仍会发送文字/参考图。第三方“不用于训练或存储”也无法仅靠本项目代码证明。

此外，隐私页开关 `ImprovementProgramToggle.tsx:40` 只写 localStorage，账户页 `account/page.tsx:112` 调用 `/api/me/improvement` 保存账号偏好后再写 localStorage；从隐私页修改不会反向同步账号记录，可能出现两处显示不同。当前未发现实际改进数据上传通道，不能声称已经违反关闭选择上传了训练数据。

建议按功能说明数据去向，区分用户主动生图、账号认证与可选改进计划；统一偏好的权威存储及同步规则，上传能力接入前验证拒绝状态。第三方留存承诺应有实际条款/协议依据。此项只判断事实准确性，不作法律结论。

### 11. P2：测试与发布工具需要从“数量”转向关键行为覆盖

当前有 178 个 `*.test.ts` 文件，默认 npm test 是 Node test runner；没有发现 `.github/workflows` 或浏览器测试配置，默认测试文件中也未发现 Playwright/Puppeteer/Testing Library 使用。这不否定既有浏览器人工冒烟和独立验证脚本，但默认回归不会自动证明真实页面交互、摄像头权限、IndexedDB 和移动内存正确。

`tsconfig.json` 排除 scripts，`eslint.config.mjs:20` 也忽略 scripts；审计/发布工具主要依赖运行时测试，而这些工具会决定发布资格。建议为工具层增加单独类型检查与适量静态检查，不必把所有 Python/训练逻辑并入 Next 构建。

优先补 6 条浏览器回归：上传→25 笔→重置、原尺寸导出、图库→AI 参考比例、AI→本地收录→AR、登录过期续期、切换多份共享纹理。真机性能和视觉质量继续作为独立验收；不要把浏览器冒烟当成真实设备或模型质量通过。

### 12. P2：文档与实现规模已经造成维护负担

审查前技术白皮书约 1.02 MB，当前状态、历史实验、操作记录混排；§3 已写 candidate57 TEST HOLD，§11.1 却仍指向“首次读取 test100”。旧状态可能误导后续 Agent 重复已禁止评估。账户实现和图库闭环也有遗漏登记。

代码层 `ArView.tsx`、`NailArtPicker.tsx` 都超过千行；同一组件同时维护摄像头/推理/绘制/资源与 UI 状态，局部修补成本较高。建议保持白皮书为简明权威入口，把历史快照归档并链接；当前模型状态从单一决策文件生成。按相机生命周期、纹理资源、识别状态、绘制几何拆分 hooks/模块，先锁定行为再逐步拆分，避免一次性重写。

## 推荐推进顺序

1. 先封闭可直接造成成本和身份错误的缺口：AI 费用保护、生产短信与续期、验证码台账、手机换绑一致性、隐私事实。
2. 并行修复低成本可见缺陷：编辑器原图基线/原尺寸导出、比例映射、共享纹理释放。
3. 在下一次正式评估前完成：逐实例质量接入最终门、测试消费台账、明确新开发/校准/最终留出角色。保持既有失败候选 HOLD。
4. 补可重复的用户流程回归、固定运行时与 CI，再围绕真实人工修正成本做下一轮模型改进和多设备/Beta验收。

不建议现在仅为了“现代化”迁移整个框架、引入微服务或放宽数据质量门。当前有价值的基础是来源隔离、完整真值审核、候选锁与已有产品链路，应保留并补齐执行缺口。
